# Repository Guidelines

## Project Structure & Module Organization

- Source: `src/` (feature folders such as `clients/`, `core/`, `services/`, `repositories/`, `utils/`, `controllers/`, `constants/`).
- Tests live beside code as `*.spec.ts` (e.g., `src/core/profit-rate/profit-rate.spec.ts`).
- Entry points: `src/index.ts` (bot), `src/server.ts` (API). Experimental MM code lives in `src/dirty-work/`.
- Build output: `dist/` (generated by TypeScript).

## Build, Test, and Development Commands

- `pnpm install`: install dependencies (pnpm is required).
- `pnpm dev`: run the arbitrage bot in dev via `tsx`.
- `pnpm api`: start the API server in dev.
- `pnpm dirty-work`: run the market‑making demo.
- `pnpm test`: run Vitest; pass a file path to scope (e.g., `pnpm test src/utils/round/round.spec.ts`).
- `pnpm lint` / `pnpm format`: check and fix style with ESLint/Prettier.
- `pnpm typecheck`: run TypeScript type checking.
- `pnpm build` and `pnpm start`: compile to `dist/` and run.

## Coding Style & Naming Conventions

- Language: TypeScript (`strict` mode). Indent 2 spaces; single quotes; trailing commas; width 80 (see `.prettierrc`).
- Linting: ESLint with `@typescript-eslint`, `vitest`, and `unused-imports` (focused tests and unused imports are errors).
- Naming: functions and factories use `createXxx…` (e.g., `createMexcOrder`); files use kebab‑case where practical; colocate test and implementation.
- Prefer functional style and small pure modules; avoid classes unless necessary.

## Testing Guidelines

- Framework: Vitest with setup in `src/test-setup.ts`.
- File naming: `*.spec.ts` next to the unit under test.
- Coverage: add/maintain tests for new logic paths and edge cases (e.g., empty orderbooks, API failures).
- CI hygiene: do not commit focused specs (`it.only`, `describe.only`)—blocked by ESLint.

## Commit & Pull Request Guidelines

- Branch format: `feat/spicy-<issue>-<slug>` or `refactor/spicy-…` (see README examples).
- Commit messages: concise, imperative, and scoped (JP/EN both fine). Group related changes.
- PRs must include: clear summary, linked issue, test updates, and any config/docs changes. Add sample logs or screenshots when touching runtime behavior.

## Security & Configuration Tips

- Copy `.env.example` to `.env` and set required keys (Discord webhooks, exchange API keys). Never commit secrets.
- Use Node 20+ and run with `pnpm`. Avoid `npm/yarn` to stay consistent with lockfile and scripts.
