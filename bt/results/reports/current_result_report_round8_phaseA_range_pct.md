### train PF < 1.0 に関する注記

全ケースで train PF が 0.77〜0.92 と 1.0 未満にもかかわらず train return がプラスになっている。
これは期末に保有在庫が BTC 価格上昇によって未実現益を含んでいる可能性を示す。
PF は実現済みトレードベースで計算されるため、未実現益は PF に反映されない。
この乖離が実際の戦略評価を歪めている可能性があり、PF のみでの評価は不完全。

## ボトルネック分析

### 1. OOS oos_return_pct が閾値 0.0% を超えない

全 30 件でOOS return がマイナス。最も良いケース（range=0.02, levels=2）でも -0.13%。

原因仮説:

- train 期間（例: 2025-10）と OOS 期間（例: 2025-11〜12）で市場レジームが異なる。
- グリッドレンジを広げると OOS でのトレード頻度が下がり（levels=2, range=0.02 で 376〜378 trades）、回収機会が減る。
- train PF < 1.0 の問題が示す通り、戦略自体の期待値がそもそもマイナス圏に近い可能性。

### 2. overfit が解消されない（range=0.025 を除く）

range=0.025 で overfit=False になったのは train return もマイナスだからであり、改善ではない。
range=0.015〜0.02 では train プラス・OOS マイナスの典型的なオーバーフィット構造が継続している。

原因仮説:

- グリッドパラメータが train 期間に特化したフィットを生んでいる。
- OOS 期間が短い場合（例: 1〜2ヶ月）、OOS での収益が安定しない。

### 3. train PF と train return の乖離

PF < 1.0 でも train return がプラスになるメカニズムが未検証のまま。
これにより「良いパラメータ」の判断基準が曖昧になっている。

## 所見

1. **range=0.02 が現時点の最有望パラメータ帯。** OOS 損失が最小で、levels=2 では -0.13% と閾値 0.0% に最も近い。

2. **levels は低いほど OOS 安定性が高い。** levels=4 は train での高いリターンを記録するが OOS での劣化が激しく、採用候補から外れる。

3. **range=0.025 は現状のトレード頻度では成立しない。** levels=2 で 234 trades、levels=3 で 531 trades と、十分な統計量が得られていない可能性がある。range を広げると price discovery（板が薄い領域）になる問題もある。

4. **OOS return が 0.0% を超えるためには、train 期間と OOS 期間の市場特性の一致、もしくは戦略自体の期待値のプラス化が必要。** 現状の戦略ロジックでは PF が 1.0 を超えていないため、根本的な改善が必要。

5. **fill_failure_rate の影響は軽微。** フィル率を変えても OOS パフォーマンスへの影響は 0.01〜0.02% 程度であり、このパラメータへの最適化は優先度が低い。

## 次アクション

### パラメータ調整案

**案1: range=0.02 を中心に微調整（優先度高）**

- range_pct を 0.018〜0.022 の範囲で 0.001 刻みで再探索。
- levels=2〜3 に絞る（levels=4 は除外）。
- order_size_ratio=0.015 固定（0.012 は train がマイナスになるため不採用）。
- fill_failure_rate=0.0〜0.02 に絞る（0.05 は効果が最小）。

**案2: leverage の探索（現状はすべて 1.0）**

- leverage=1.0 のみで実施してきたが、leverage=0.5 でリスクを下げ OOS の損失縮小を確認する。
- ただし leverage を下げると return も比例して下がるため、OOS oos_return_pct の改善には直接寄与しない。

### 追加BT設計

**案A: OOS 期間の延長**

- 現状の OOS 期間が短い（1〜2ヶ月）と推定される場合、OOS 期間を 3〜4ヶ月に延長して評価の統計的信頼性を向上させる。

**案B: walk-forward 検証の導入**

- 固定 train/OOS 分割ではなく、rolling window で train→OOS を複数回繰り返し、overfit 感度を検証する。
- 例: train 3ヶ月 + OOS 1ヶ月を 1ヶ月ずつスライドして 6 window 評価。

**案C: train PF と return 乖離の原因調査**

- 期末在庫の未実現損益を明示的に分離し、「実現済み return」と「未実現込み return」を区別したメトリクスを追加する。
- PF < 1.0 かつ return がプラスのケースが戦略として有効かどうかの判断基準を明確化する。

### リスク管理の見直し

- levels=2 で range=0.02 の場合、OOS DD が 0.23% と低水準。現行の `max_oos_dd_pct=8.0` はこの戦略には過剰に緩い閾値。採用基準を `max_oos_dd_pct: 1.0` 程度に厳格化しても同じ結果になる点を確認する（このラウンドは DD 問題ではなく return 問題で不採用）。
- 採用閾値 `min_oos_return_pct: 0.0` が未達のため、閾値を一時的に `-0.1`（-0.1%）に緩和してパラメータの挙動を観察することも選択肢の一つ。ただし実運用投入前に別途 robustness 検証が必要。

### ロジック改善提案

- **train PF < 1.0 問題の解決**: グリッドボットの利益ロジックを確認し、未実現益の扱いを明示的に定義する。期末にオープンポジションを強制クローズしたシミュレーション結果と比較する。
- **OOS でのトレード頻度確認**: levels=2, range=0.02 で OOS 376〜378 trades が適切かどうかを確認。train で 378 trades に対して OOS で同等のトレード頻度が出ているかを検証する。
- **BTC 相場レジーム別の条件分岐**: train 期間が強気相場、OOS 期間が横ばいまたは弱気相場である場合、異なるパラメータセットが必要になる。レジーム分類ロジックの追加を検討する。
